一、这个项目是什么

它由三层组成，每层回答一个问题：

层回答什么问题代码
运行时Agent 怎么循环、怎么花钱、怎么不出错src/arlab/ 约 3000 行
垂直应用拿它做了什么有用的事apps/kb_agent/ 约 560 行
评测体系怎么证明它做得好/不好，好多少贯穿 stages/evaluate/judge/scoring/report

垂直应用做的是技术文档检索问答：索引了 77 篇中文 LLM/RAG 技术资料（1450 个切片）， 能回答「PagedAttention 解决了什么问题」这类问题，并且每句结论都挂着原文逐字引用。

为什么需要一个垂直应用？因为通用 runtime 本身不可演示。「我写了个 Agent 框架」在面试里是空的， 「它能回答我私有的 1450 个文档切片，每句话能追到原文，53 条题集 3 轮 0.947」才是实的。

二、整体架构

用户问题 / 评测题目 │ ▼ ┌─────────────────────────────────────────────┐ │ Agent.run(task) │ │ │ │ system prompt = 角色 + 工具说明 + 运行限制 │ │ + 技能目录（只有名字+描述） │ │ + DOMAIN_PROMPT（垂直层） │ │ │ │ while True: │ │ ① 查预算 → 耗尽就关检索工具、保留交付通道 │ │ ② 调 LLM（流式，记 TTFT） │ │ ③ 解析 tool_calls │ │ ④ 逐个执行：schema 校验 → 权限检查 → 执行 │ │ ⑤ 结果回填 messages │ │ ⑥ 命中终止型工具 → validator 门禁 → 交付 │ │ ⑦ 每一步写 trace.jsonl │ └─────────────────────────────────────────────┘ │ ▼ trace.jsonl（过程证据） │ ├──► stages.py 10 阶段判定（机械判据） ├──► judge.py LLM 归因（只在失败时跑） ├──► scoring.py 加权质量分 + 闸门 └──► report.py 三栏 HTML 报告

关键设计：过程和结果分开存。模型答对了但路径违规，分数照样扣； 答错了但过程合规，能定位到具体哪一步出的问题。这就是「结果对不算对，路径合规才算过」。

三、核心模块逐个讲

3.1 主循环 loop.py（238 行）

整个 Agent 的本体不到 250 行，核心就是这个 while：

while True:
    reason = self.budget.exhausted()      # ① 先查预算
    tools = self.registry.schemas()

    if reason:                             # 耗尽 → 收尾模式
        messages.append({"role":"user","content":FINISH_NUDGE})
        tools = self.registry.terminal_schemas()   # 只留交付通道！
        nudged = True

    reply = self.llm.chat(messages, tools=tools)   # ② 调模型
    self.budget.charge(reply.usage.total)
    self.trace.llm_call(...)                        # ③ 落盘

    tool_calls = reply.message.get("tool_calls") or []

    if not tool_calls:                     # ④ 没调工具
        if has_terminal and content and not pushed_submit:
            push_back_to_submit()          #   绕过交付通道 → 推一次
            continue
        return AgentResult(answer=content, status=...)

    for call in tool_calls:                # ⑤ 执行工具
        result = self._exec_tool_call(call, step)
        if spec.terminal and result.ok:
            if spec.validator:             # ⑥ 交付门禁
                reason = spec.validator(payload)
                if reason: continue        #   不通过 → 打回去改
            return AgentResult(answer=args)  # 参数即交付物

每一处 if 背后都是一次实测踩坑，下面逐个说。

为什么要「终止型工具」？

最原始的做法是让模型直接输出文本，然后正则抠 JSON。实测失败：提示词写得再好， 模型也会在 8~12/12 之间抖——某个答案里多一句「好的，以下是结果」就解析不了。

改成「模型必须调用 submit_answer(answer, citations, refused)」之后，格式由 JSON Schema 校验保证，模型想交付就必须传合法参数。

这是整个项目最重要的一条规律：任何「希望模型自觉」的约束，都会在压力下失效。 只有写进运行时、不通过就直接拒绝的，才靠得住。

为什么收尾时要保留交付通道？

原始代码在预算耗尽时执行 tools = []——把 submit_answer 也一起关了。 结果模型只能裸输出文本，格式必然失败。

实测数据：4 条失败里全部是「内容全对、只是没走工具」。改法是 terminal_schemas()：

def terminal_schemas(self):
    """只留终止型工具。预算耗尽收尾时用——关掉检索，但不关交付通道。"""
    return [t.openai_schema() for t in self.tools.values() if t.terminal]

效果：格式 FAIL 9 → 2，质量分 0.890 → 0.901。

3.2 预算 budget.py（59 行）

四类预算，按「代价从小到大」检查——先查便宜的，避免为了算 token 而浪费时间：

维度作用超限后果
步数最多几轮 LLM 调用强制收尾
token总消耗上限（40k）强制收尾
时间墙钟上限（240s）强制收尾
连续失败连续 3 次工具失败判定卡死，提前中止
def exhausted(self):
    """返回超限原因；还没超返回 None。按代价从小到大检查。"""
    if self.steps >= L: max_steps:      return "steps"
    if self.tokens >= L.max_tokens:   return "tokens"
    if self.elapsed() >= L.max_seconds: return "time"
    if self.consecutive_failures >= 3:  return "consecutive_failures"
    return None

3.3 工具与权限 tools/registry.py（180 行）

每个工具声明三样东西：JSON Schema（参数长什么样）、权限级别（read/write/net）、 是否终止型（调用即交付）。

@dataclass
class Tool:
    name: str
    description: str
    parameters: dict
    handler: Callable
    permission: str = "read"      # read / write / net
    terminal: bool = False         # 调用即结束，参数就是交付物
    validator: Callable | None = None  # 交付门禁

权限分级不是装饰。评测时 Registry(allow={"read"})，写文件的工具根本不会出现在 schema 列表里——模型想调也调不到，不是「调了被拒绝」，是看不见。

所有工具失败都变成 ok=False 的结果，不向上抛异常：

def call(self, name, raw_args):
    """执行一次工具调用。任何失败都变成 ok=False 的结果，不向上抛。"""
    try:
        args = json.loads(raw_args)          # 参数不是 JSON
    except JSONDecodeError:
        return ToolResult(ok=False, error="bad_json")
    err = validate(args, schema)             # schema 不符
    if err: return ToolResult(ok=False, error=f"schema: {err}")
    if tool.permission not in self.allow:    # 权限不足
        return ToolResult(ok=False, error="permission_denied")
    if not self.tools.get(name):             # 工具不存在
        return ToolResult(ok=False, error="unknown_tool")
    try:
        return ToolResult(ok=True, output=str(fn(**args)))
    except Exception as e:                   # 工具内部炸了
        return ToolResult(ok=False, error=f"exception: {e}")

五种错误码各对应一个评测阶段的判据：

错误码含义归属阶段
unknown_tool模型编了个不存在的工具工具有效性
bad_json参数不是合法 JSON参数合法性
schema: ...字段缺失/类型错参数合法性
permission_denied越权调用工具有效性
exception: ...工具实现内部报错错误恢复

3.4 技能系统 skills.py（115 行）

技能是 Markdown 文件，带 YAML 头：

---

（正文，只有模型主动加载才看得到）

渐进披露：system prompt 里只放「名字 + 一句话描述」，正文要模型自己调 load_skill 才会注入。理由：正文动辄上千 token，全塞进 prompt 既贵又稀释注意力。

但这个机制实测是失败的。3 轮基线的数据：

通过率
加载了技能93.1%（108/116）
没加载技能93.5%（29/31）

而且 21 个任务都出现过「有时加载有时不加载」——加载与否是随机的， 不是根据任务需要判断的。详见 坑 12。

3.5 轨迹 trace.py（140 行）

每跑一步写一行 JSONL，五类事件：

事件包含
llm_call步数、token、延迟、TTFT、成本、提供的工具、finish_reason
tool_call工具名、参数、结果、成功与否、错误码
fault_injection注入了什么故障
run_end最终答案、状态、总步数、总 token
fingerprint输入指纹（见 4.6）

为什么落盘而不是存内存：评测失败后要能回放。10 阶段的所有判据都是从这份 JSONL 重新算出来的，不依赖运行时的任何中间状态。意味着改了判据可以拿旧 trace 复判， 不用重跑（省了真金白银）。

3.6 LLM 客户端 llm.py（276 行）

三个关键点：

① 流式只为了拿 TTFT。非流式调用只能拿到「整个响应有多久」， 而用户真正感受到的是「多久开始出字」。

def _chat_stream(self, payload):
    """流式调用，主要为了拿到 TTFT。"""
    first_token_at = None
    for line in resp:
        chunk = parse_sse(line)
        if first_token_at is None and has_content(chunk):
            first_token_at = time.monotonic()   # ← 首字时间
        # tool_calls 分片按 index 拼接（不能简单字符串相加）
        merge_tool_call_deltas(acc, chunk)

② tool_calls 分片要按 index 拼。流式返回的 tool_calls 是被切碎的， {"index":0,"function":{"arguments":"{\"a\""}} 这样一段段来， 必须按 index 聚合再拼字符串，否则参数永远解析不了。

③ 流式失败退回非流式。某些网关对流式支持不好，加了 ARLAB_STREAM=0 开关兜底。

3.7 计价 pricing.py（89 行）

从网关的 /v1/models 里读 pricing 字段，缓存到本地。 读不到就显示 —，绝不写死一个数字假装知道。

def human(amount, currency):
    """钱要按量级选精度，否则会显示成 0.00 或 0.0000001"""
    if amount >= 1:    return f"${amount:.2f}"

这就是为什么报告里每任务成本是 $0.00441 而不是 $0.00。

四、评测体系（这个项目真正的技术含量）

4.1 为什么不能只测「答对没有」

第一版评测只有一层：答案里含不含期望字符串。结果立刻出事：

期望模型输出子串匹配实际
80「总销售额 180 元」✅ 通过❌ 错
B「Below is the analysis」✅ 通过❌ 错

「180」里含「80」，「Below」里含「B」——数字和字母的包含关系不是语义正确。

改法两层：① 断言结构化（json_field，取值再比）② 判据从 trace 事件流派生，不看最终文本。

4.2 10 个阶段的分工

#阶段判据（机械可核验）能抓什么
1探查是否盲猜路径：第一次 read_file 就报「文件不存在」= 盲猜不看目录直接猜文件名
2工具路径必选工具调了没 / 禁用工具调了没 / 故障时不改用违规工具该查库却去联网
3工具有效性unknown_tool / permission_denied 计数编造不存在的工具
4参数合法性bad_json / schema 违反计数参数结构错
5错误恢复失败后是否换策略（同参数重试 = 没换）死磕同一个错
6技能召回声明的 expected_skills 有没有被 load_skill没想起该用的手册
7执行效率步数 / token 是否超 stage_limits；到 80% 算 WARN绕远路、烧 token
8终止决策status 是 ok 还是 budget_exhausted被预算逼停
9输出格式交付物是否满足 schemaJSON 不合规
10答案正确业务断言（引用能否逐字找到、要点是否覆盖、块是否命中）内容错

顺序 = 漏斗：前面的阶段失败会污染后面的判定。格式不合规时「答案」判 N/A 而不是 FAIL——否则一个逗号级的问题会扣掉 35% 权重。

阶段是怎么从 8 涨到 10 的

版本变化触发原因
8 阶段探查 / 有效性 / 参数 / 恢复 / 技能 / 效率 / 终止 / 答案端到端只有总分，说不出哪一环掉
9 阶段拆出「输出格式」4 条失败内容全对，只是 Markdown
10 阶段加「工具路径」+ 一票否决「结果对不算对，路径合规才算过」

4.3 判分与归因必须分离

反模式：让 LLM 当裁判打分。

如果分数由模型给，那「改了 prompt 分数涨了」这件事无法证明是真的——可能是裁判当天心情不同。 所以分成两条独立路径：

判分 stages.py + scoring.py归因 judge.py
输入trace 事件流失败现场（题、答案、错因、时间线）
方法确定性代码，无模型LLM 读日志写诊断
输出PASS / WARN / FAIL / N/A错误类型 + 根因 + 证据 + 修复建议
影响分数吗是否
跑几次每条都跑只在失败时跑

归因的 8 种固定错误类型（不让模型自由发挥）：

ERROR_TYPES = [
  "reasoning_error",   # 推理错
  "output_format",     # 格式不合规
  "tool_misuse",       # 用错工具
  "prompt_ambiguity",  # 任务本身没说清
  "context_missing",   # 缺必要上下文
  "hallucination",     # 编造
  "skill_miss",        # 该用技能没用
  "other",
]

为什么固定枚举：自由文本的诊断无法聚合。固定 8 类之后，53 条题可以统计出 「hallucination 占 40%」这种能驱动决策的结论。

4.4 三硬指标

只报准确率是自欺。三个必须同时报：

指标怎么测为什么不能省
准确率10 阶段加权分 + 及格线及格线，但不代表能用
延迟TTFT（流式取首字）+ 端到端 P50/P99用户等 2 分钟就会关掉
成本token × 网关单价，逐任务累加答对但每单倒贴钱，照样不能上线

TTFT 必须流式测。非流式调用拿到的延迟是「整段生成完」的时间， 而用户感受的是「多久开始出字」，两者实测差 10 倍以上（3.0s vs 40.1s）。

4.5 多轮区间：单点分数不可信

第一次做 3 轮重复时发现：同配置、同题集，两轮能差 0.28（0.889 vs 0.608）。 后来稳定下来，区间也有 0.016 宽。

题集规模3 轮质量分区间宽度
13 条（仅黄金）0.916 / 0.873 / 0.8710.045
53 条（黄金+白银）0.951 / 0.947 / 0.9350.016

推论：任何小于 0.016 的「改进」都是噪声。而在 13 条时，任何小于 0.045 的都是噪声—— 那意味着我早期报告的所有「提升」都不可信。

def _merge_repeats(paths, args):
    """把 N 轮结果合成一份：准确率给区间，延迟和成本合并样本。"""
    scores = [r["score"]["quality"] for r in runs]
    merged["score"]["quality"]      = median(scores)
    merged["score"]["quality_range"] = [min(scores), max(scores)]
    merged["score"]["quality_all"]   = scores
    # 延迟/成本：合并所有样本，样本量 ×N
    merged["latency"]["samples"] = sum(r["latency"]["samples"] for r in runs)

4.6 输入指纹：改了一个标点也要能发现

用户提的要求是：「每修改一次 prompt 就要重新跑测试，哪怕只改了一个标点」。

口头规则守不住，所以做成机制——把影响模型行为的东西全部哈希：

参与指纹为什么
system prompt 全文改一个字行为就变
每个技能的正文（逐个）能定位是哪个技能变了
题集文件全文改注释、调顺序也算改测试
模型名换模型等于换系统
运行参数步数/token/温度
def _h(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:16]

def _skill_hashes(skills_dir):
    """按技能名记录正文哈希。整个 SKILL.md 参与计算，前端元数据也算。"""
    return {p.parent.name: _h(p.read_text()) for p in Path(skills_dir).glob("*/SKILL.md")}

不做任何归一化——不 trim、不合并空格、不忽略大小写。因为「只是多了一个空格」也可能改变模型行为。

配套脚本 scripts/prompt_guard.py：对比当前指纹和上次通过测试的指纹， 不一致就退出码 1，可以直接挂 CI。

4.7 故障注入：看它是报错还是瞎编

「结果对不算对，路径合规才算过」的另一半是：工具坏掉的时候，它会不会编一个正常答案。

class FaultInjector:
    """第 at_call 次调用 tool 时返回失败。"""
    def intercept(self, name):
        if name != self.tool: return None
        self.count += 1
        if self.count == self.at_call:
            return f"[注入故障] {self.tool} 暂时不可用"
        return None

挂在 registry 入口，对工具实现零侵入。题目里声明：

{
  "id": "g13_fault_search",
  "prompt": "...",
  "inject_fault": {"tool": "kb_search", "at_call": 2},
  "checks": [{"type": "predicate", "name": "reports_failure"}]
}

判定谓词 pred_reports_failure：答案必须说明「检索失败」， 如果它编了一个看起来很正常的答案 → 直接 0 分。

4.8 A/B 对照与统计检验

改完跑一遍跟上一遍比，是弱证据——没有控制变量。所以做了真正的 A/B：

./run.sh eval --no-skills       # A 组：不提供技能
./run.sh eval --inline-skills   # B 组：技能正文内联
./run.sh eval                   # C 组：按需加载（默认）

同一批 53 条题、同一模型，唯一变量是技能怎么提供。判据用 McNemar 配对检验 （同一批题跑两次的正确做法，不是普通卡方）：

b, c = 只有B通过的数量, 只有A通过的数量
chi2 = (abs(b-c) - 1)**2 / (b + c)     # df=1，临界值 3.84 @ p=0.05

结果：三组差异全部不显著（p≈0.45~0.48）。详见 第八章。

4.9 三档数据集：对外只能报黄金集

档规模来源用途
冒烟5 条手写验证链路通不通，不报数
黄金13 条人工核验 + 标准答案对外报数、验收
白银40 条从语料程序化生成只做回归，不报绝对值

白银集不能对外报。它由脚本从语料里抽问句生成（期望块 = 本块或同文档后继块）， 质量参差。它的价值是「改了一行代码，看这 40 条有没有大面积掉」， 而不是「我的系统有 0.94」。

五、垂直应用：kb_agent

通用 runtime 只提供「读文件 / 写文件 / 列目录 / 跑代码 / 加载技能」。 垂直层不改造运行时，只替换工具集——这是设计上的关键：同一套引擎，换工具就是另一个产品。

5.1 三个工具，各司其职

工具返回什么为什么这样设计
kb_search(query, k, mode)chunk_id + 160 字摘要 + 相关度只给摘要不给全文——全文一次几百字，6 条就上千 token；摘要让模型先判断值不值得读
kb_read(chunk_id)该块完整原文引用必须来自这里，因为摘要是截断的
cite_check(quote, chunk_id)逐字命中 / 未命中唯一能机械判定「有没有编造」的检查
def cite_check(quote: str, chunk_id: str) -> str:
    """逐字校验引用。这是唯一能机械判定「有没有编造」的检查。"""
    text = _store().chunk(chunk_id).text
    if quote.strip() in text:
        return "命中"
    return f"未命中：该引文不在 {chunk_id} 的原文里"

不提供 web_search 的引用能力。知识库里没有的问题，联网搜来的内容 不能作为「资料依据」——那等于允许它用外部信息冒充内部资料。这条在题目里用 forbidden_tools 硬性禁止。

5.2 交付门禁：编造的引用提交不进去

这是整个项目里最有价值的一个机制。起因是一次真实事故（详见坑 13）。

原来只有 cite_check 工具——建议性的，模型可以不用。改成 submit_answer 的 validator，在交付前强制校验：

def validate_submission(payload: dict) -> str | None:
    """交付门禁：每条引文必须能在对应 chunk 里逐字找到，否则提交不进去。"""
    cites = payload.get("citations")
    if not isinstance(cites, list):
        return "citations 必须是数组"
    if not cites and payload.get("refused") is not True:
        return "没有给任何引用，也没标 refused=true"

    bad = []
    for i, c in enumerate(cites, 1):
        quote, cid = c.get("quote","").strip(), c.get("chunk_id","").strip()
        if not quote or not cid:
            bad.append(f"第 {i} 条缺 quote 或 chunk_id"); continue
        if quote not in _store().chunk(cid).text:
            bad.append(f"第 {i} 条的引文在原文里找不到：{quote[:36]!r}")
    return "；".join(bad[:4]) if bad else None

运行时侧只需要三行：

if spec.terminal and result.ok:
    if spec.validator:
        reason = spec.validator(payload)
        if reason:
            messages.append({"role":"tool","tool_call_id":...,
                             "content": f"提交被拒绝：{reason}\n请修正后重新调用。"})
            continue          # ← 打回去，不交付

实测五种情况全部按预期：

输入结果
真实引文✅ 放行
编造的引文🚫 拒绝
不存在的 chunk_id🚫 拒绝
无引用也不标拒答🚫 拒绝
拒答（refused=true，无引用）✅ 放行
8 条真 + 2 条假🚫 整单拒绝

5.3 六个判定谓词

谓词是应用层注册的自定义判据，返回 None=通过，返回字符串=失败原因。 它们让通用 runtime 不需要知道「检索问答」这回事。

谓词判什么
citations_grounded每条引文必须在其 chunk 原文里逐字存在，且至少一条
answer_covers要点覆盖：must 列表里至少命中 N 个
not_refused有答案的题不能拒答（防止一拒了之）
chunk_hit引用必须命中期望块（白银集用：本块或同文档后继块）
states_missing资料确实没有时：要么标 refused，要么正文说明缺失
reports_failure工具故障时，答案必须说明失败，不能编正常答案

5.4 为什么黄金集只有 13 条

人工核验一条题需要：确认标准答案正确、确认期望 chunk 真的含有这个答案、写要点列表。 13 条是能和白银集配合的最小可用规模。

白银集 40 条是脚本生成的（scripts/gen_silver.py）：从 chunks 里抽问句 → 期望块 = 本块或同文档后继块 → 过滤掉碎片化、带序号残留、过短的句子。 它的作用是回归，不是验收。

七、踩过的坑（18 个）

这一章是全文最有价值的部分。每一个坑都是「先判断错、被数据打脸、才找到真因」。

坑 1 · 以为电脑没有 GPU

现象：nvidia-smi: command not found，我据此判断「这台机器没有 GPU，微调做不了」。

真因：WSL 里 nvidia-smi 在 /usr/lib/wsl/lib/，不在 PATH。 直接执行那个完整路径，输出：RTX 4060 Laptop 8G / 驱动 566.43 / CUDA 12.7。

教训：「工具没装」和「工具不在 PATH 里」是两件完全不同的事。

坑 2 · 以为 WSL 可以提到 16GB 内存

现象：24 核 CPU，直觉认为内存不会小。想把 .wslconfig 的 memory 提到 16GB。

真因：查 Win32_ComputerSystem 发现物理内存只有 15.7GB， Windows 侧当时仅剩 2.1GB 可用。提到 16GB 会让整机假死。

教训：先量再改。虚拟机上限不能超过宿主物理内存。

坑 3 · 子串匹配的假阳性

现象：5 条任务全过，看起来系统很好。

真因：断言是「答案里包含期望字符串」。"180" 包含 "80"， "Below" 包含 "B"——模型答错了也判通过。

改法：断言结构化（json_field：先解析 JSON 再按字段取值比较）。

坑 4 · isinstance(True, int) 是 True

现象：自己写的 JSON Schema 校验放过了 {"count": true}。

真因：Python 里 bool 是 int 的子类，isinstance(True, int) == True。

改法：validate() 对 bool 单独拦截。这个 bug 是单测抓到的，不是人工 review 发现的。

坑 5 · embedding 模型加载卡死 7 分钟

现象：第一次检索请求超时 124 秒，以为代码死循环。

真因：用 faulthandler.dump_traceback_later(45) 打出调用栈，定位到 sentence-transformers 在查 HuggingFace Hub 的 revision，网络阻塞。

改法：设 HF_HUB_OFFLINE=1 / TRANSFORMERS_OFFLINE=1。首跳 50s → 2s。

坑 6 · 「限读 5 块能省 token」——完全错了

现象：成本偏高，直觉是「读的块太多」，于是限制最多读 5 块。

真因：算相关性发现——token 与「步数」相关 0.939，与「工具调用数」只有 0.396， 而且成本随步数近似平方增长（每步都要把完整历史重新发一遍）。

改法：不限制块数，改限制步数。技能里写「步数比块数贵」。

坑 7 · 在技能开头写「要快」反而变慢了

现象：想让它少绕路，在技能第一行写「务必高效，减少步数」。

真因：这段话破坏了技能的召回——description 和正文的语义漂移， 模型更少去加载它。质量分从 0.923 掉到 0.772。

改法：回滚。技能正文只写「怎么做」，不写「要努力」。

坑 8 · 以为提示词能保证 JSON 格式

现象：在 system prompt 里详细规定了 JSON 结构，以为够了。

真因：实测格式遵循率在 8/12 ~ 12/12 之间随机抖。模型会加「好的，以下是结果」这种前缀。

改法：submit_answer 工具 + JSON Schema。格式由 runtime 保证，不靠模型记性。

坑 9 · 预算耗尽时把交付通道也关了

现象：白银集 40 条里有 10 条格式失败，全都「内容正确但没走工具」。

真因：收尾逻辑写的是 tools = []——把 submit_answer 一起禁用了。 模型只能裸输出文本，格式必然失败。

改法：terminal_schemas() 只留交付工具。格式 FAIL 9 → 2，质量分 0.890 → 0.901。

坑 10 · 以为「兜底推一次」能救格式

现象：模型绕过工具时，追加一句「请调用 submit_answer」再试一次。

真因：10 → 9，几乎无效。因为真因是坑 9（通道被关），不是模型忘了。

教训：症状和原因常在不同层。「加一句提示」是最便宜的修法，也最容易掩盖真问题。

坑 11 · 阈值 25000 是拍脑袋定的

现象：效率阶段的 token 上限写死 25000，导致 57% 的任务都超标。

真因：实际中位数是 27879——上限比中位数还低，注定大面积失败。

改法：scripts/calibrate_limits.py 按历史 P90 写回。25000 → 57472，超标率 57% → 10%。 并且脚本会打印提醒：阈值调高会让效率指标变好看，报告必须同时显示实际中位数。

坑 12 · 技能在空转（最贵的一个发现）

现象：技能召回阶段一直有 FAIL，但任务都答对了。

真因：统计 3 轮基线——加载技能 93.1% 通过，没加载 93.5% 通过，零差异。 而且 21 个任务都出现过「有时加载有时不加载」，说明加载与否是随机的。

根本原因：原技能写的是「先检索再读全文」「引用要逐字」——模型本来就会。 写进技能唯一的效果是让人以为系统具备它并不具备的能力。

教训：不是所有东西都该做成 skill。留着空转的技能比没有更糟。

坑 13 · 调了 8 次 cite_check，提交了 10 条引用

现象：某条题失败，报「2 条引用无法溯源」。

真因：查 trace 发现——cite_check 调了 8 次全部通过，但最终提交 10 条。 多出的 2 条从没检查过，而且是编的（原文里根本没有那两句话）。

改法：cite_check 是建议性的（模型可跳过），改成 submit_answer 的 validator——提交不进去，必须回去复制原句。

坑 14 · 评测跑的从来不是生产配置

现象：改了 DOMAIN_PROMPT（领域提示词），分数纹丝不动。

真因：生产路径 cmd_ask 传了 extra_system=DOMAIN_PROMPT， 而评测路径 run_suite 没传。评测的 agent 从来没有领域提示词。

这意味着：所有历史评测数据都是「无领域提示词」版本， 「改 prompt 无效」的结论不是提示词没用，是它根本没被加载。

改法：run_suite 补传 + 预算参数抽成常量 + 新增 tests/test_parity.py （6 条测试锁住「评测 = 生产」，含反向断言：extra_system 再被漏传必须变红）。

坑 15 · 用单轮 A/B 改了架构，结果被 3 轮推翻

现象：单轮 A/B 显示「内联技能 0.943 vs 无技能 0.927」，于是把内联改成默认。

真因：3 轮定型基线跑完——内联 0.944 vs 按需 0.947，质量没变， 但 token +32%、成本 +28%、端到端 +7.8s。单轮那 0.016 的差异就是噪声本身。

改法：回退内联为对照开关。教训写进代码注释—— 我刚写完「0.045 以内都是噪声」，转头就用 0.016 改了默认配置。

坑 16 · 管道掩盖了退出码

现象：A/B 实验「跑完了」，但两个结果文件都不存在。

真因：命令是 ./run.sh eval --out x.json | tail -12 && ./run.sh eval ...。 $? 是 tail 的退出码（0），不是 python 的。第一个命令参数错误退出， && 照样执行了第二个。

教训：判断命令成功与否，不能用管道末尾命令的退出码。

坑 17 · 循环导入

现象：evaluate.py 和 stages.py 互相 import 对方。

真因：两边都要用 extract_json / dig（从模型输出抠 JSON）。

改法：抽成 jsonx.py 这个纯工具模块，两边都只依赖它。

坑 18 · 复判脚本切片越界

现象：想拿旧 trace 复判，脚本取前 12 个 gold 目录，结果混进了白银集的目录。

真因：目录按名字排序，eval-g* 和 eval-s* 相邻， 切片 [:12] 刚好跨过边界。

改法：改用 report_v3.html 的 mtime 作时间参照，取它之前的 12 个目录。

8.4 三个最重要的结论

① 单点分数不可信，区间才可信。
13 条题集 3 轮区间宽 0.045，53 条收窄到 0.016。所以「改进」必须超过 0.02 才算真的变了。 我早期报的所有小于 0.045 的「提升」都是噪声。

② 评测必须等于生产。
曾经评测路径漏传 extra_system，导致所有评测都在「无领域提示词」下跑。 这类 bug 不报错、不崩溃，只是让所有结论悄悄失真。现在用 6 条测试锁死。

③ 方向错了，修不了。
发现 bug 能修；发现「技能层可能根本没用」，只能承认。 三次数据（按需 93.1% vs 93.5%、内联 0.943 vs 0.927、3 轮 0.944 vs 0.947） 全部落在噪声内——这个结论比任何一个优化都值钱。

十、面试怎么讲

10.1 一句话版本

「我写了一个 Agent 运行时和一个技术文档问答应用，配了一套 10 阶段的评测体系。 53 条题集 3 轮中位质量分 0.947（±0.008），首字 3 秒，端到端 40 秒，每任务 0.44 美分。 最有意思的是我用三组 A/B 证明了我自己写的技能层没有价值，然后把它降级了。」

最后那句是钩子——面试官一定会问「你怎么证明的」，然后你就可以讲统计检验和架构回退。

10.2 三个可以展开的故事

故事讲了什么能力
软约束 → 硬拦截
格式靠 schema、引用靠 validator、绕过靠中止		知道模型不可靠，用工程手段兜底
评测与生产不一致
改 prompt 分数不动，因为评测根本没加载那个 prompt		会怀疑自己的测量工具

10.3 三句不能说错的话

① 不能说「技能提升了准确率」
数据三次不支持。可以说「证明了按需加载机制失效（命中率 75% 且随机）」。

② 不能说「准确率 94.7%」而不说条件和区间
必须带「53 条题集、3 轮、中位、区间 ±0.008」。单点数字在 53 条样本上不可信。

③ 不能说语料是自己做的
77 篇来自 wdndev/llm_interview_note 和 km1994/AIGC-Interview-Book 两个公开仓库。 主动说明反而加分——它证明你知道 RAG 项目里「语料」和「工程」的边界。

10.4 如果被追问「这有什么难的」
