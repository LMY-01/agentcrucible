# 检索问答

## 第一铁律：步数比块数贵

每一次「读一块 → 想一想 → 再搜一次」都会多花一整步，而**每一步都要把全部历史重发一遍**，
成本随步数平方增长。实测：同样读 19 个块，走 6 步花 21881 token，走 7 步花 50448。

所以：**能在一个回合里并行发出去的调用，就不要分回合。**
一次 assistant 回合里同时发 3 个 `kb_search`、4 个 `kb_read` 都是允许的，成本只算一步。

反面做法（很常见，也很贵）：
```
搜 → 读一块 → 搜 → 读一块 → 搜 → 读一块 ……
```
正面做法：
```
一次并行搜 3 个不同问法 + 一次并行读 4 个最相关的块 → 作答
```

## 流程

1. **先检索，再读全文，最后才回答。**
   `kb_search` 只给摘要，摘要看着像答案也要 `kb_read` 确认——摘要截断处常常漏掉关键限定条件（"通常"、"除…之外"、"仅当"）。

2. **一次不够就换词再检索。**
   检索结果相关度前三条都低于 0.01，或者摘要都在讲别的东西，说明用词不对。
   换文档里的术语重试，不要用大白话硬扛。

3. **同一问题拆成子问题，并行检索。**
   "A 和 B 有什么区别"要分别检索 A 和 B，再对比。两个 `kb_search` **同时发**，不要先搜完 A 再搜 B。

4. **每条结论都要挂引用，引用必须逐字。**
   写完引文先跑 `cite_check`，未命中就回 `kb_read` 复制原句。
   多个引文可以并行 `cite_check`。

## 输出格式

严格输出 JSON，不要加解释文字：

```json
{
  "answer": "结论，分点写，每个分点后面用 [1][2] 标出处",
  "citations": [
    {"id": 1, "chunk_id": "从 kb_search 拿到的 id", "quote": "原文逐字片段"}
  ],
  "refused": false
}
```

## 禁止

- 禁止用 `kb_search` 的摘要当引文——摘要是我截断过的，原文里没有这句话。
- 禁止凭已有知识补全文档没写的内容。
- 禁止一条引用都不给就下结论。

## 什么情况停下来

翻两次检索、读了三四个块仍然找不到直接依据 → 不要硬凑，加载 `refusal-policy` 并按它的规则作答。
