# kb-agent — 技术文档检索问答

在 `arlab` 通用运行时上落地的**垂直应用**。运行时一行没改，只换了两样东西：工具集、技能集。

```
任务「LoRA 的核心思想是什么？」
  ↓
┌─────────────────────────────────────────────┐
│ arlab 运行时（循环 / 预算 / 工具权限 / trace）│
└─────────────────────────────────────────────┘
   工具: kb_search · kb_read · cite_check        技能: retrieval-qa · refusal-policy
   索引: /mnt/d/kb-lab（1450 个 chunk，77 篇中文 LLM/RAG 技术资料）
```

## 为什么这么切工具

| 工具 | 只允许做什么 | 设计理由 |
|---|---|---|
| `kb_search` | 返回 `chunk_id` + 摘要（160 字）+ 相关度，**不含全文** | 逼 Agent 判断「摘要够不够」。一次把库倒进上下文，既贵又看不出它到底理解了没有 |
| `kb_read` | 按 id 取全文 | 明确的一跳，token 花在哪一目了然 |
| `cite_check(quote, chunk_id)` | 检查这句引文是否在该 chunk 里**逐字**存在 | **这一层的核心**。让 Agent 自己验证引用，而不是靠 prompt 祈祷它别编 |

第三个工具解决的问题：检索类应用最典型的失败不是答错，是**答得像**——把摘要改写成引文、把两段的句子拼成一句、用「一般来说」包装猜测。这些靠人读一遍才能发现。`cite_check` 把它变成一次工具调用。

## 为什么这套判据不需要领域专家

黄金集的标准答案不是「我认为对的答案」，而是「**文档里那句话**」。所以判据全是机械可核验的：

| 谓词 | 判什么 | 需要懂领域吗 |
|---|---|---|
| `citations_grounded` | 每条 `quote` 是否在其 `chunk_id` 的原文里逐字出现 | ❌ 只需要能判断「这句话在不在原文里」 |
| `answer_covers` | 答案是否覆盖预设要点（`must` 命中 N 个） | 🟡 要点从参考答案里挑，不用自己写 |
| `states_missing` | 资料确实没有时，是否老实说明缺失 | ❌ |
| `not_refused` | 资料里有答案时，不许拒答 | ❌ |

这是检索类应用能自动化评测的关键：**引用可溯源，就不需要人来判断内容对不对**。

## 实测：一次 prompt 改动的 A/B

12 条黄金集（8 条有答案 + 4 条拒答），`bailian/qwen3.8-flash`。

**v1 的问题是格式写在技能里**：`retrieval-qa` 技能里规定了输出 JSON，system prompt 只说「格式见技能」。
结果部分任务没加载技能，答案内容完全正确但输出成了 Markdown —— 格式失败被算成内容失败。

| | 通过 | 质量分 | 技能召回 | 答案正确 | 执行效率 | 终止决策 |
|---|---|---|---|---|---|---|
| v1 格式写在技能里 | 10/12 | 0.868 ❌ | 6/8 | 10/12 | 4/12 | 11/12 |
| **v2 格式写进 system prompt** | **11/12** | **0.923 ✅** | **8/8** | 11/12 | 5/12 | **12/12** |

**结论：格式是接口契约，属于运行时；检索策略才属于技能。**
把格式放进需要「想起来」的地方，等于赌模型每次都会记得查手册——它不会。
技能该承载的是判断（什么时候多跳、什么时候拒答），不该承载下游要解析的字段结构。

### 剩下的两个真问题

**① 模型会编造 `chunk_id`。**
v2 唯一失败的那条，引用的 `chunk_id` 是 `检索增强llm__检索增强llm-0000`，
而 `kb_search` 从没返回过这个 id——它照着命名规律自己拼了一个。
`citations_grounded` 抓到了（`chunk_id 不存在`），这就是「引用必须可溯源」的价值：
内容读起来毫无破绽，只有机械校验能发现出处是假的。

**② token 的真实驱动因素是「步数」，不是「读了几块」。**

我原本以为是 `kb_read` 读太多块导致超支，打算在技能里加「最多读 5 个块」。
把 12 条的成本拆开算，结论反过来了：

| 任务 | 步 | 工具调用 | token | token/步 |
|---|---|---|---|---|
| g08_react | 4 | 6 | 9849 | 2462 |
| g05_lora_init | 4 | 7 | 12267 | 3066 |
| g02_hyde_idea | 6 | **19** | 21881 | 3646 |
| g07_paged_attention | 7 | **19** | 50448 | 7206 |
| g10_refuse_dim | 7 | 11 | 48350 | 6907 |

- token 与**步数**的相关系数：**0.939**
- token 与**工具调用数**的相关系数：0.396

g02 调了 19 次工具只花 21881，g10 只调 11 次却花 48350。差别全在步数上。

而 `token/步` 从 4 步的 2462 涨到 7 步的 7206 —— 比值 2.93，
步数比值 1.75，接近平方（1.75² = 3.06）。**成本是随步数平方增长的**，
因为每次 LLM 调用都要把 system prompt 加全部历史重发一遍。

所以正确的优化不是「少读几块」，是「**少走几步**」：
- g07 的正确姿势是**一步并行发 4 个 `kb_read`**，而不是 4 步各读 1 个
- 或者在技能里改掉「读一块→想一想→再搜一次」的串行习惯

把「最多读 5 个块」写进技能反而会做反：块数少了它就得再多搜几轮，步数更多。

**③ 拒答可能是被逼出来的，不是判断出来的。**

v1 里 `g09_refuse_version` 用了 56562 token、状态 `budget_exhausted`，但它被判 PASS——
因为收尾时它确实说了「知识库中没有 vLLM 0.4.2 的更新日志」。

同一句话，两种含义：
- 检索两轮没找到 → **策略正确**
- 撞了 7 步预算墙才收尾 → **只是被逼到墙角**

旧判据只看文本，区分不了。修法是把运行时事实传给谓词看：

```python
if ctx.get("status") == "budget_exhausted":
    return "拒答是被预算逼停后收尾的，不是自己判断出资料缺失"
```

用真实 trace 复判确认：旧判据 PASS（假阳性），新判据 FAIL 并指出 `token 56562 步数 7`。

**这条值得单独记一笔**：评测体系本身也会骗人，而且骗得比模型更隐蔽——模型答错你能看出来，
判据放宽你只会看到一个漂亮的分数。所以每加一条谓词，都要问一句「它能不能区分『做对了』和『碰巧看起来对』」。

## 用法

```bash
./run.sh ask "LoRA 里 A 和 B 矩阵为什么要这样初始化？"
./run.sh eval                      # 跑 12 条黄金集
./run.sh eval --limit 3            # 跑前三条
./run.sh eval --no-judge           # 跳过失败归因，省调用
```

复用 `/mnt/d/kb-lab` 的索引和 venv（`~/venvs/kb-lab`），不重复下载 embedding 模型。

## 踩过的坑

**`sentence_transformers` 加载权重前会向 HuggingFace Hub 查 revision。**
WSL 里这个请求不可达，会阻塞到 TCP 超时——表现是「程序卡死」，实测超过 7 分钟没动静。
`faulthandler.dump_traceback_later()` 打栈才看出来卡在 `hf_api.model_info`。

修法：`run.sh` 和 `kb_tools.py` 里都设 `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1`，
权重本地已缓存，首跳从几十秒压到 2 秒。

## 已知局限

- 黄金集 12 条，其中 8 条有答案、4 条拒答；标准答案从 kb-lab 已有的 qa.json 迁移，**未经独立复核**
- 只有单跳检索，还没有多跳（「A 和 B 有什么区别」需要分别检索再对比）
- 语料只有 77 篇，规模太小，分数只能横向比较，不能对外宣称准确率
