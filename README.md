# AgentCrucible

[![tests](https://github.com/LMY-01/agentcrucible/actions/workflows/test.yml/badge.svg)](https://github.com/LMY-01/agentcrucible/actions/workflows/test.yml)

**An agent runtime that can prove itself.** 把 Agent 放进十个阶段的熔炉里，看它在哪一步裂开。

一个能讲清楚每个设计决定的 Agent 运行时：**工具权限分级、预算耗尽降级、逐步轨迹落盘、
10 阶段断言式评测、三硬指标（准确率/延迟/成本）并排报数**。

零第三方依赖（纯标准库），任何 OpenAI 兼容端点都能跑。

仓库分两层：

```
src/arlab/          通用运行时 —— 循环、预算、工具权限、技能加载、trace、11 阶段评测
apps/kb_agent/      垂直应用 —— 技术文档检索问答，只换工具集和技能集，运行时零改动
```

垂直层的存在是为了回答「你用它做了什么」：同一套引擎，挂上 `kb_search/kb_read/cite_check`
就变成一个能带引用作答、能自查引用真伪、知道何时该拒答的问答 Agent。

**对外可报的基线**：117 条题集（gold 38 + holdout 19 + 多跳 20 + 白银 40）跑 3 轮，
中位质量分 **0.964**（区间 [0.960, 0.975]），通过率中位 **92.31%**，首字 **3.7s**，
端到端 **50.4s P50**，每任务 **$0.00555**。评测判据全是机械可核验的（引用能否在原文逐字找到），
不需要领域专家判断答案对不对 —— 详见 [`apps/kb_agent/README.md`](apps/kb_agent/README.md)
和 [`runs/p3_final_report.md`](runs/p3_final_report.md)。

```
任务
 └─ Agent.run()
     ├─ system prompt（角色 + 技能目录 + 运行限制）
     ├─ loop: LLM → 解析 tool_calls → 校验 → 执行 → 结果回填
     │    ├─ 预算检查（步数 / token / 时间 / 连续失败）
     │    └─ 每一步写 trace.jsonl
     └─ 无 tool_calls → 最终答案；预算耗尽 → 关工具 + 强制收尾
```

## 三个和"能跑的 demo"不一样的地方

### 1. 技能用渐进披露，不是全塞进 prompt

`skills/*/SKILL.md` 只把 `name` + `description` 放进系统提示，正文由模型自己判断要不要用 `load_skill` 拉。

理由：技能正文动辄几千 token，十几个技能全塞进去既贵又稀释注意力。这是 Anthropic Agent Skills 的机制，也是"skill 体系"在工程上的真实含义——**难点不在格式，在于让模型在正确的时机想起正确的手册**。

```
【可用技能目录】
- csv-profiling: 给 CSV 做数据画像并输出标准化报告。当任务要求分析表格数据…时加载。
- error-recovery: 工具调用失败后的排查流程。当工具返回错误、找不到文件…时加载。
```

### 2. 工具失败被记成指标，不是异常

`Registry.call()` 里任何失败——未知工具名、参数不是合法 JSON、schema 校验不过、权限不足、handler 抛异常——都返回 `ToolResult(ok=False, error=<类型>)`，附一段给人看的中文错误，交给模型自己纠正。

这样"无效工具调用率"变成一个可测的数字。如果失败直接抛异常，这条流水线只能告诉你"崩了"，说不出崩在哪个环节。

至于参数校验，写完单测立刻抓到一个真 bug：`isinstance(True, int)` 在 Python 里成立，导致 JSON Schema 声明 `integer` 的字段会接受 `true`。修法是在类型检查前把 bool 单独挡掉。

### 3. 预算耗尽要降级，不能崩

`Budget.exhausted()` 返回 `steps` / `tokens` / `time` / `tool_failures` 之一。loop 拿到后不是 raise，而是：**关掉工具 + 注入一条"必须收尾"指令 + 再请求一次**。模型被逼着把已有信息整理成答案，`status` 记成 `budget_exhausted`。

线上 agent 超时崩掉会丢掉全部中间结果；这一条是所有玩具实现和能上线的实现之间的分界线。

## 实测

模型 `bailian/qwen3.8-flash`，5 条任务跑两遍（`temperature=0`）：

| 任务 | 结果 | 步数 | 工具调用 | 失败 | token | 耗时 |
|---|---|---|---|---|---|---|
| t01_sum 单文件聚合 | ✅ | 3 | 3 | 0 | 3933 | 12.1s |
| t02_join 双文件关联 | ✅ | 4 | 4 | 0 | 7327 | 18.5s |
| t03_skill 按技能规范出报告 | ✅ | 4 | 4 | 0 | 8759 | 38.0s |
| t04_honest 资料不存在时拒答 | ✅ | 4 | 3 | 0 | 4839 | 12.2s |
| t05_recover 文件名不对后自救 | ✅ | 4 | 4 | 1 | 4862 | 9.3s |

| run | 成功率 | 平均步数 | 工具调用 | 失败 | 无效率 | 平均 token |
|---|---|---|---|---|---|---|
| 第一次 | 5/5 | 3.8 | 19 | 2 | 10.5% | 6132 |
| 第二次 | 5/5 | 3.8 | 18 | 1 | 5.6% | 5944 |

两遍成功率、平均步数完全一致，token 相差 3%。**波动只在工具调用次数上，来源单一**：t04 拒答任务第一遍多撞了一次不存在的文件才转向 `list_dir`，第二遍直接开始探查。

这一点本身就值得记下来：`temperature=0` 不等于确定——网关侧仍有非确定性，所以单个数字不能当结论，得看两遍以上是否稳定。

那 1–2 次失败都是**预期内**的：t05 先读了 `data.csv`（不存在），`read_file` 报错后 `list_dir` 发现真实文件名是 `data_2024.csv` 并纠正——这正是"错误可恢复"的证据，trace 里完整留着现场：

```
step 1  list_dir                     ok    39ms
step 1  read_file  {data.csv}        FAIL   5ms   error=exception
step 2  read_file  {data_2024.csv}   ok    41ms
step 3  run_python                   ok    40ms
step 4  → 答案
```

离线单测 51 条，不联网：`PYTHONPATH=src python -m unittest discover -s tests`

## 分阶段评测

端到端只回答「过没过」。同样的 5/5，可能是干净利落过的，也可能是靠撞报错纠错过——
后者换个文件名、换个模型就崩。所以除了最终断言，再从 trace 里派生 11 个阶段判定，
全部是**确定性判据，不调模型**：

| 阶段 | 判据 |
|---|---|
| 探查 | 读文件前有没有确认工作区真实内容。盲猜文件名为 FAIL；并行探查 + 盲猜为 WARN |
| 工具路径 | 是否调用必选工具、避开禁止工具，失败后不降级到禁止路径 |
| 工具有效性 | 无 `unknown_tool` / `permission_denied` |
| 参数合法性 | 无 `bad_json` / `schema` 违约 |
| 错误恢复 | 失败后是否换了参数。同参数重试为 FAIL |
| 技能召回 | 缺 required 且答案错为 FAIL、答案对为 WARN 待归因；optional 未加载不扣分 |
| 效率成本 | 步数 / token 超校准阈值只记 WARN，不进质量分 |
| 效率浪费 | 同参数重试、重复读同一块、连续无进展为 FAIL |
| 终止决策 | 模型自行收尾，还是被预算逼停 |
| 输出格式 | 要求结构化交付时，答案必须是可解析 JSON |
| 答案正确 | 原有断言 |

四级判定 `pass / warn / fail / na`。warn 单列，因为它和 fail 的处理方式完全不同：
fail 要改设计，warn 通常只要改提示词；混在一起会让人去改错的地方。

同一套任务跑三遍（`bailian/qwen3.8-flash`）：

| 阶段 | PASS | WARN | FAIL | N/A | 结论 |
|---|---|---|---|---|---|
| 探查 | 3 | 0 | 0 | 12 | 只有 t05 考察此阶段 |
| 工具有效性 | 15 | 0 | 0 | 0 | 稳定 |
| 参数合法性 | 15 | 0 | 0 | 0 | 稳定 |
| 错误恢复 | 0 | 0 | 0 | 15 | **从未被触发** |
| 技能召回 | 3 | 0 | 0 | 12 | 只有 t03 考察此阶段 |
| 执行效率 | 8 | 7 | 0 | 0 | t01/t03/t04 在 PASS 与 WARN 间抖动 |
| 终止决策 | 15 | 0 | 0 | 0 | 稳定 |
| 答案正确 | 15 | 0 | 0 | 0 | 全绿，但存在天花板效应 |

三条从这张表读出来的结论：

1. **8 个阶段里有 2 个基本没被覆盖。** 错误恢复 15 次全是 N/A——三轮合计 50 次工具调用、
   **失败 0 次**，连可观测的失败样本都不存在。这个阶段等于没测。缺的不是运气，是一条能稳定
   制造失败的用例；这是**评测集的缺口，不是运行时的**。
2. **执行效率的 WARN 是阈值问题，不是模型问题。** 上限 5 步、模型在 3~4 步之间正常波动，
   `4/5 = 80%` 就告警，等于把正常抖动报成缺陷。阈值该按历史分布定，而不是拍一个 0.8。
3. **答案正确 15/15，区分度不够。** 5 条任务对这个模型太容易，全绿说明不了运行时好，
   只说明题目简单。要加难度分层（多约束、长链条）才有横向比较的价值。

复现：

```bash
./run.sh eval --out runs/stage_run_1.json    # 跑三遍
~/venvs/arlab/bin/python scripts/analyze_runs.py runs/stage_run_*.json
```

`analyze_runs.py` 会把每个任务每个阶段的级别按 run 对齐，并区分两类问题：**稳定 fail**
（设计或提示词的问题，改完应该看到级别整体上移）和**抖动**（模型侧不确定性，改提示词收益有限，
得靠运行时机制兜住）。

## 评测报告：先找问题，再给建议，最后才打分

三件事按**优先级**排，不是按执行顺序：

| 优先级 | 做什么 | 代码 |
|---|---|---|
| 1 | **发现问题** — 10 阶段细粒度判定，定位到「哪个环节、哪类错误」 | `stages.py` |
| 2 | **给出建议** — LLM 读失败轨迹，产出错误类型 + 根因 + 证据 + 可执行的修复动作 | `judge.py` |
| 3 | **并排对照** — 输入材料 / 模型输出 / 标准答案三栏并列，扣分原因贴在同一张卡上 | `report.py` |
| 4 | **衡量质量** — 加权分 + 及格线闸门，作为能不能上线的守门员 | `scoring.py` |

质量分放最后，是因为前两件事不该依赖它：先看清哪里烂，才知道那个数字该怎么读。

```bash
./run.sh eval                     # 跑完自动生成 HTML 报告
./run.sh eval --no-judge          # 跳过归因（省一次模型调用）
./run.sh eval --threshold 0.95    # 改闸门，低于它返回非零退出码
./run.sh eval --no-report         # 只出 json
```

判分和归因**必须分开**：判分用确定性断言，谁跑都一样；归因用模型读 trace，产出的是带置信度的假设。
混在一起就是让运动员当裁判，分数没法比。

### 质量分的口径

权重写在 `scoring.py` 里，因为它是口径不是参数：

| 阶段 | 权重 | 理由 |
|---|---|---|
| 答案正确 | 0.35 | 最终交付物仍然最重要 |
| 输出格式 | 0.05 | 内容正确但下游解析不了，也是交付失败 |
| 工具有效性 | 0.15 | 调错工具直接决定这轮能不能用 |
| 工具路径 | 0.05 | 权重不高，但违规有一票否决权 |
| 参数合法性 | 0.10 | 参数不会写等于工具不会用 |
| 探查 | 0.10 | 盲猜路径是可靠性问题，线上会放大 |
| 错误恢复 | 0.10 | 失败能不能自己爬出来 |
| 技能召回 | 0.05 | 只保留 required 候选的约束，optional 不扣分 |
| 效率成本 | 0.00 | 成本由三硬指标报告，不在质量分里重复扣 |
| 效率浪费 | 0.05 | 同参数重试、重复读块、无进展循环才是真实浪费 |
| 终止决策 | 0.05 | 会不会被预算逼停 |

`na` 阶段剔除后把剩余权重归一化——任务不考察探查，不该因此扣分。
`warn` 计半分。

### 负对照

`t06_control` 是一条**故意设计成必败**的任务，用来持续验证「失败能被定位、能被归因、能并排对照」这条链路没坏。
它不计入任何统计（阶段汇总、质量分、通过率都排除），只出现在报告的对照区。

这条任务第一次跑就抓到真问题：归因模块指出「这题的期望值和题面自相矛盾，是判分器的问题」——
说明归因不是只会劝你改提示词。

## 三硬指标：准确率 / 延迟 / 成本

只报准确率的评测报告是不完整的。99% 准确率但用户等两分钟、或每单倒贴钱，系统照样上不了线。
所以每次评测固定输出三项：

| 指标 | 怎么测 | 为什么必须 |
|---|---|---|
| **准确率** | 质量分 + 通过率（结果评估 + 轨迹评估 10 阶段） | 业务准入的及格线 |
| **延迟** | **TTFT**（首字时间，靠流式拿第一段 delta 的时间戳）+ 端到端 P50/P95/P99 | 用户体感是「多久开始看到字」，不是「总共花了多久」 |
| **成本** | token × 网关 `/v1/models` 返回的 `pricing` 单价 | token 数对工程师有意义，对拍板的人没有 |

关键实现细节：

- **TTFT 必须走流式**。非流式接口只能告诉你总耗时，拿不到首字时间。带推理的模型上这
  两者差很多——实测 `reasoning_tokens=163` 时首字 3.8s、总耗时 5.1s。
  `ARLAB_STREAM=0` 可以关掉退回非流式（此时 TTFT = 总耗时，会在报告里标明）。
- **单价从网关读，不写死**。写死了换模型就错。读不到时显示 `—` 而不是给一个假数字。
- **P99 说清采样口径**。现在是任务级百分位（跨 13 条任务），严格 P99 需要 `--repeat` 多轮
  采样，报告里直接标注了这句限制。

实测一条（`g01_rag_problems`，qwen3.8-flash）：

```
三硬指标 ────────────────────────────────────────
  准确率  质量分 0.500   通过 0/1
  延迟    TTFT 3.8s(P50)   端到端 45.9s(P50) 最慢 45.9s
  成本    $0.00455 总计 / $0.00455 每任务   共 33626 token
```

这张表能直接回答老板的三个问题：**干得对不对、用户等不等得起、一单亏不亏**。

## 评测纪律：改一个字也要重跑（做成了机制）

口头规则守不住——改 prompt 的时候没人会想起三个月前那个 0.923 是怎么来的。
所以每次评测都记录**输入指纹**：

| 进指纹的东西 | 为什么 |
|---|---|
| system prompt 全文 | 改措辞会改输出分布 |
| 每个技能的内容（分开记） | 能定位到「是哪个技能变了」 |
| 题集全文 | 改题目、调顺序、改注释都算 |
| 模型名 | 换模型当然要重测 |
| 运行参数（步数/token/时间上限） | 改预算直接改结果 |

**不做任何归一化**：空白、标点、全角半角都算变更。
这是刻意的——「我以为只是改了个逗号」恰恰是最容易漏测的那一类。

```bash
PYTHONPATH=src:. python scripts/prompt_guard.py --kind kb   # 检查垂直层
PYTHONPATH=src:. python scripts/prompt_guard.py --kind runtime
```

输出长这样：

```
最近一次评测: eval_1794474829.json
  质量分 0.923  闸门 pass  记录指纹 a1b2c3d4e5f6a7b8
  当前指纹   f6a7b8c9d0e1f2a3

⚠ 检测到变更，上次的分数已经失效：
  · 技能内容变了: retrieval-qa
  · system prompt 变了（1204 → 1350 字）

请重跑：./run.sh eval
```

退出码 1，可以直接接 pre-commit 或 CI。

### 这条规则为什么不是洁癖

见 [`apps/kb_agent/README.md`](apps/kb_agent/README.md) 里的「反例：一次改坏的 prompt」——
我往技能里加了一段看起来完全合理的「减少步数」建议，结果质量分从 0.923 掉到 0.772，
失败原因是从没预料到的方向：技能开头写「要快」，模型就跳过了加载技能，而输出格式正好在技能里。

**prompt 没有小改动。** 任何一处措辞都可能在别处产生副作用，而且副作用的方向通常不是你能推出来的。

## 已知局限

- **多跳样本只有 20 条**：样本量偏小、置信区间偏宽，扩到 30 条以上结论才更稳。
- **效率成本已移出质量分**：超阈值只作为 WARN 和成本报告，效率浪费才扣分；与旧版分数比较时必须注意口径变化。
- **required 技能的消融样本仍小**：目前只有 4 条完成三轮消融并降为 optional，不能直接推广到全部任务。
- **多跳 token 只验证了一个变量**：80 字摘要仅省 6.63% token，通过率中位数却下降 10 个百分点，已否决并保留 160 字；其他优化空间仍在。
- **holdout 仍明显低于 dev**：三轮质量分中位 0.924、通过率中位 84.21%，不能用 dev 成绩外推泛化能力。
- **判据会假阴性**：今天累计发现 5 次——「未能」「拦下」「不会」漏在拒绝词表外、`<script>` 转义被误判、多跳题锁死文档 ID 把等价证据判成没证据。判据和被测系统一样需要校准，而现在校准靠人工读 trace。
- **安全 ASR 4.8% 不是 0**：出口过滤是正则，挡不住有创造力的输出（值拆行就能绕过）。要根治只能不给模型看敏感文件。
- **历史压缩没做**：目前只有单条工具结果截断（4000 字符，保留头尾），没有把中间对话摘要成一条。长任务会撞上下文上限。
- **没有子 agent**：任务是线性的，没有「拆解 → 并行 → 汇总」。
- **没有多轮对话**：一次 run 一个任务，memory 不跨 run。
- **语料是公开资料**：不是业务场景。换语料要重建全部题集，这是唯一无法靠技巧绕过的短板。
